Presence System API

REST API of the NFC-based Attendance Management and Verification System — a Spring Boot backend that turns badge scans on an ACR122U reader into verified attendance records, and lets administrators correct them from a web dashboard.

Full API reference OpenAPI spec Source on GitHub

Overview

The API is split in two families. The public one is called by the hardware client; the protected one backs the administration dashboard.

MethodPathAuthPurpose
POST /api/v1/attendances None Register an attendance from a card scan
GET /api/admin/me ADMIN Validate credentials, return the caller
GET /api/admin/attendances ADMIN List every attendance record
POST /api/admin/attendances ADMIN Create a record manually
PUT /api/admin/attendances ADMIN Update an existing record
DELETE /api/admin/attendances ADMIN Delete a record

Base URL

Running the stack locally with Docker Compose, the backend listens on:

http://localhost:8080

Authentication

Every route under /api/admin/** requires HTTP Basic authentication with a user holding the ADMIN role. Passwords are stored BCrypt-hashed and verified against the users table. 

curl -u admin:password http://localhost:8080/api/admin/me

POST /api/v1/attendances is deliberately left open so the NFC terminal can post without carrying credentials. CSRF protection is disabled, and CORS accepts only http://localhost:* and http://127.0.0.1:* origins, with credentials allowed.

Registering an attendance

The reader sends the card UID and its own identifier. The server resolves the student from the card, derives the room from the reader id (the L prefix becomes S), finds the course running in that room at that instant, and stores a present record stamped with the current time. 

curl -X POST http://localhost:8080/api/v1/attendances \
  -H "Content-Type: application/json" \
  -d '{"readerId": "L1101", "cardId": "04A3B2C1"}'

A successful call returns 200 OK with a plain-text confirmation. The call is rejected with 400 Bad Request in three cases:

ScenarioStatus
Valid check-in200 OK
Unknown card UID400 Bad Request
No course scheduled in the room right now400 Bad Request
Student already checked in for that course400 Bad Request

readerId must be exactly 5 characters and cardId exactly 8 — both are enforced by Jakarta Validation before the request reaches the service.

Managing records as an administrator

Records are addressed by the studentId + courseId pair rather than a surrogate id. POST and PUT carry that pair in the body; DELETE passes it as query parameters.

List

curl -u admin:password http://localhost:8080/api/admin/attendances

Create

curl -u admin:password -X POST http://localhost:8080/api/admin/attendances \
  -H "Content-Type: application/json" \
  -d '{
        "studentId": "E001",
        "courseId": "C001",
        "status": "absent justifie",
        "arrivalTime": null,
        "justification": "Certificat médical"
      }'

Update

curl -u admin:password -X PUT http://localhost:8080/api/admin/attendances \
  -H "Content-Type: application/json" \
  -d '{
        "studentId": "E001",
        "courseId": "C001",
        "status": "present",
        "arrivalTime": "08:15:00",
        "justification": null
      }'

Delete

curl -u admin:password -X DELETE \
  "http://localhost:8080/api/admin/attendances?studentId=E001&courseId=C001"

status accepts only present or absent justifie. Anything else fails validation with 400 Bad Request.

Data model

AttendanceDto is what the admin endpoints return — a record joined with the student, course and room it belongs to. 

{
  "studentId":       "E001",
  "studentFullName": "Eric Beaubrun",
  "courseId":        "C001",
  "courseDate":      "2026-08-05",
  "courseStartTime": "08:00:00",
  "courseEndTime":   "10:00:00",
  "roomId":          "S1101",
  "status":          "present",
  "arrivalTime":     "08:15:00",
  "justification":   null
}

Field-by-field constraints, request schemas and every response code live in the full reference, generated from openapi.yaml.

How this documentation is built

openapi.yaml is not written by hand. A GitHub Actions workflow boots the application against a throwaway PostgreSQL, exports the specification that springdoc derives from the controllers, and commits it back to docs/ — so the reference cannot drift from the code.

To change what appears here, edit the @Operation, @ApiResponse and @Schema annotations in src/main/java/…/infrastructure/web/. When the application is running, the same specification is served live at /v3/api-docs.yaml, with an interactive Swagger UI at /swagger-ui.html.
