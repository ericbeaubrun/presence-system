API Presence System

API REST du système de gestion et de vérification des présences par NFC — un backend Spring Boot qui transforme les badgeages effectués sur un lecteur ACR122U en enregistrements de présence vérifiés, et permet aux administrateurs de les corriger depuis un tableau de bord web.

Référence complète de l’API Spécification OpenAPI Code source sur GitHub

Vue d’ensemble

L’API se divise en deux familles. La première, publique, est appelée par le client matériel ; la seconde, protégée, alimente le tableau de bord d’administration.

MéthodeCheminAuthRôle
POST /api/v1/attendances Aucune Enregistrer une présence à partir d’un badgeage
GET /api/admin/me ADMIN Valider les identifiants et renvoyer l’appelant
GET /api/admin/attendances ADMIN Lister tous les enregistrements de présence
POST /api/admin/attendances ADMIN Créer un enregistrement manuellement
PUT /api/admin/attendances ADMIN Mettre à jour un enregistrement existant
DELETE /api/admin/attendances ADMIN Supprimer un enregistrement

URL de base

Lorsque la stack est lancée en local avec Docker Compose, le backend écoute sur :

http://localhost:8080

Authentification

Toutes les routes sous /api/admin/** exigent une authentification HTTP Basic avec un utilisateur possédant le rôle ADMIN. Les mots de passe sont stockés hachés avec BCrypt et vérifiés contre la table users. 

curl -u admin:password http://localhost:8080/api/admin/me

POST /api/v1/attendances est volontairement laissée ouverte afin que le terminal NFC puisse envoyer ses requêtes sans transporter d’identifiants. La protection CSRF est désactivée et le CORS n’accepte que les origines http://localhost:* et http://127.0.0.1:*, avec les identifiants autorisés.

Enregistrer une présence

Le lecteur envoie l’UID de la carte ainsi que son propre identifiant. Le serveur retrouve l’étudiant à partir de la carte, déduit la salle de l’identifiant du lecteur (le préfixe L devient S), recherche le cours qui se déroule dans cette salle à cet instant, puis enregistre une présence present horodatée à l’heure courante. 

curl -X POST http://localhost:8080/api/v1/attendances \
  -H "Content-Type: application/json" \
  -d '{"readerId": "L1101", "cardId": "04A3B2C1"}'

Un appel réussi renvoie 200 OK avec une confirmation en texte brut. L’appel est rejeté avec 400 Bad Request dans trois cas :

ScénarioStatut
Badgeage valide200 OK
UID de carte inconnu400 Bad Request
Aucun cours programmé dans la salle à cet instant400 Bad Request
Étudiant déjà pointé pour ce cours400 Bad Request

readerId doit comporter exactement 5 caractères et cardId exactement 8 — ces deux contraintes sont appliquées par Jakarta Validation avant que la requête n’atteigne le service.

Gérer les enregistrements en tant qu’administrateur

Les enregistrements sont identifiés par le couple studentId + courseId plutôt que par un identifiant technique. POST et PUT transmettent ce couple dans le corps de la requête ; DELETE le passe en paramètres de requête.

Lister

curl -u admin:password http://localhost:8080/api/admin/attendances

Créer

curl -u admin:password -X POST http://localhost:8080/api/admin/attendances \
  -H "Content-Type: application/json" \
  -d '{
        "studentId": "E001",
        "courseId": "C001",
        "status": "absent justifie",
        "arrivalTime": null,
        "justification": "Certificat médical"
      }'

Mettre à jour

curl -u admin:password -X PUT http://localhost:8080/api/admin/attendances \
  -H "Content-Type: application/json" \
  -d '{
        "studentId": "E001",
        "courseId": "C001",
        "status": "present",
        "arrivalTime": "08:15:00",
        "justification": null
      }'

Supprimer

curl -u admin:password -X DELETE \
  "http://localhost:8080/api/admin/attendances?studentId=E001&courseId=C001"

status n’accepte que present ou absent justifie. Toute autre valeur échoue à la validation avec un 400 Bad Request.

Modèle de données

AttendanceDto est ce que renvoient les endpoints d’administration — un enregistrement joint à l’étudiant, au cours et à la salle auxquels il se rattache. 

{
  "studentId":       "E001",
  "studentFullName": "Eric Beaubrun",
  "courseId":        "C001",
  "courseDate":      "2026-08-05",
  "courseStartTime": "08:00:00",
  "courseEndTime":   "10:00:00",
  "roomId":          "S1101",
  "status":          "present",
  "arrivalTime":     "08:15:00",
  "justification":   null
}

Les contraintes champ par champ, les schémas de requête et l’ensemble des codes de réponse figurent dans la référence complète, générée à partir de openapi.yaml.

Comment cette documentation est construite

openapi.yaml n’est pas écrit à la main. Un workflow GitHub Actions démarre l’application avec une base PostgreSQL jetable, exporte la spécification que springdoc déduit des contrôleurs, puis la commite dans docs/ — la référence ne peut donc pas diverger du code.

Pour modifier ce qui apparaît ici, éditez les annotations @Operation, @ApiResponse et @Schema dans src/main/java/…/infrastructure/web/. Lorsque l’application tourne, la même spécification est servie en direct sur /v3/api-docs.yaml, avec une interface Swagger interactive sur /swagger-ui.html.
